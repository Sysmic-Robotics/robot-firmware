## Synthetic verification (known injected delay/bias)

Fixture: A = robot @1kHz vx_est = chirp 0.5->4 Hz (+ harmonic), 5 s; B = engine
@60Hz vx = sig(t - 0.080) + 0.03 + 1% noise. Injected truth: delay 80 ms
(B lags A), bias +0.03 m/s (B relative to A).

Before fix:
  delay -80.0 ms (exact) | bias -0.0308 (magnitude exact) | correlation -0.216
  rms 0.8959  -> correlation/RMS were computed on RAW unaligned signals.

After fix (sensor_compare.py compute_stats: post-alignment recompute):
  delay -80.0 ms (exact) | correlation 0.999486 | bias -0.0295 | rms 0.0368
  verdict line flips to "1/1 variables with good correlation (>0.95)". Exit 0.

Zero-delay sanity (same chirp, no shift, 1% noise): correlation 0.999541,
bias +0.0009, delay +0.0 ms, rms 0.0210 — original path unchanged, aligned
recompute is a no-op at ~0 delay. Exit 0.

## Fix applied

compute_stats (sensor_compare.py:272-336) previously computed rms/mean/std/max/
correlation from v_high_common vs v_low_interp BEFORE delay compensation, and
recovered delay separately via normalized cross-correlation (np.correlate
mode='same', peak of |lag| <= min(500, n/4)). For a genuinely delayed fusion
signal (expected 30-100 ms) this understated correlation and inflated RMS/bias.

Added after delay_seconds is known:
  t_align = t_common - delay_seconds          (negative reported delay = lower-
  rate source lags the higher-rate one; aligning means reading the lagging
  signal at an earlier time, i.e. t_align = t_common - delay_seconds)
  valid   = t_align within [t_low[0], t_low[-1]] (skip extrapolation)
  v_low_aligned = np.interp(t_align[valid], t_low, v_low)
  recompute error/rms/mean/std/max/correlation on the aligned subset
  (fallback to raw stats when valid.sum() <= 10, i.e. no usable overlap)
JSON schema unchanged; n_points now = aligned subset length.

## IMPORTANT for the operator's T6 data runs

1. Time columns MUST be named one of: time, timestamp, t[s], t (case-
   insensitive auto-detect, sensor_compare.py:80-86) — otherwise the tool
   falls back to headers[0] raw values, which corrupts alignment (verified:
   ms-vs-s mismatch produced garbage rates/correlation). Alternatively pass
   --time-col explicitly.
2. Engine record CSV (logger) and 1kHz STM32Monitor telemetry CSV must both
   use seconds for their time column, or specify --time-col per file.
3. Delay sign convention: negative delay_seconds = file_b (lower rate) lags
   file_a (higher rate) — i.e. fusion/vision latency of the engine record.
4. Recovery is exact at >=60 Hz lower-rate sampling with a chirp/rich-spectrum
   excitation (verified -80.0 ms vs injected 80 ms). Real robot runs should
   use the T1 velocity_step_test.lua steps (rich transients) rather than
   steady-state holds for delay estimation.

DATA-CONTRACT VERIFICATION (2026-08-06, follow-up) — engine record CSV
must be FILTERED before sensor_compare (critical, empirically proven):

The engine GUI logger (engine/engine/src/logger/logger.rs:97-122) writes
13 rows per frame: 12 robot rows (team 0/1, id 0-5) + 1 ball row
(RobotID=-1), ALL sharing the same ElapsedTime (seconds, as_secs_f64).
Feeding record_*.csv to sensor_compare UNFILTERED interleaves all 12
robots' + ball's Vx_Actual into one series.

Synthetic proof (fixtures /tmp/contract_robot_1khz.csv + 
/tmp/contract_engine_60hz.csv, injected: engine lags robot by 80ms,
bias +0.03, chirp 0.5->4Hz):
  UNFILTERED: rate_lower_hz=782.7 (not 60!), corr=0.870, delay=-74ms,
              rms=0.327, bias=+0.004  -> CORRUPT, below 0.95 threshold
  FILTERED  : rate_lower_hz=60.2, corr=0.9994, delay=-80.0ms EXACT,
              bias=-0.0300 EXACT, rms=0.038  -> CLEAN

MANDATORY OPERATOR STEP before any sensor_compare engine-vs-robot run:
  awk -F, 'NR==1 || ($2==0 && $3==0)' record_vx_p1.0.csv > record_vx_p1.0_robot0.csv
  (NR==1 keeps the header; $2=RobotID==0 and $3=Team==0 keeps only the
   commanded robot; drops the ball row too)
  Then: sensor_compare ... contract_robot_1khz.csv record_vx_p1.0_robot0.csv
  Note: ElapsedTime is seconds (3 decimals) -> unit-compatible with the
  stm32monitor 'time' column; not in sensor_compare auto-detect set
  {time,timestamp,t[s],t} but the headers[0] fallback selects it correctly.
