Evidence runs (grSim --headless, DISPLAY=:1, engine rebuilt):
A. sim_smoke2.lua — open-loop vx=0.5: robot moved at measured 0.46-0.48 m/s,
   straight line, theta held; active=true while vision streamed. PASS.
B. xy_setpoint_sim.lua — set_position_target (T9 Rust PositionPID, default
   Kp=4.3745 Ki=1.8227): robot responds, but SUSTAINED LIMIT CYCLE around the
   setpoint (amplitude ~0.5-1.0 m, velocities to 1.5 m/s, never settles in 30 s)
   + theta spins up. TWO CAUSES:
     B1. T7 gains are tuned for the FIRMWARE velocity plant (T2: L=95 ms, T=245 ms).
         grSim's velocity response is much faster (~near-instant), so the loop is
         effectively delay-dominated and 4.37/s proportional gain is far above the
         stable crossover -> oscillation. If the real velocity loop proves faster
         than the T2 estimate, the operator should reduce Kp first (sim converged
         with Kp~0.6-scale gains on the fast plant).
     B2. grSim angular semantics differ from firmware: the 5th arg is vel_angular
         in rad/s (grSim) but an ABSOLUTE HEADING TARGET in rad (firmware, per
         protocol). compute_position_target sends theta_target=current heading ->
         in grSim that is positive feedback (dtheta/dt = theta) -> exponential
         spin-up. On hardware this correctly holds heading. Position-loop tuning
         MUST therefore be done on the real robot; grSim position tests must pass
         5th arg = 0.
C. xy_pi_lua.lua — T8 Lua position-loop STRUCTURE (rotation R(-theta) + PI +
   integral anti-windup, 5th arg=0) with Kp=0.6 Ki=0.15: DIAGONAL convergence
   from (-0.5,-0.5) to (0.5,0.5), decaying oscillation, settled at
   (0.500,0.500) +/- 5 mm with ~0 velocity and ~0 command by ~7 s, held for the
   remaining 35 s. Proves: rotation math (body-frame commands from field-frame
   error) correct end-to-end, PI + anti-windup stable against a fast plant with
   modest gains.
